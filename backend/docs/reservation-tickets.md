# QR-билеты и вход участников

Один постоянный QR на бронь. При группе из трёх человек можно отметить вход
двух, а затем одного. Простая проверка не изменяет счётчик. Существующие ответы
списка/деталей броней не менялись, токены в них не добавлены.

## Подготовка backend

Установить обновлённые зависимости (`qrcode==8.2` генерирует SVG без Pillow).
Перед запуском новой версии на существующей БД применить миграцию
`b4c6d8e0f2a1` (после `a3b5c7d9e1f2`) обычным способом проекта, например:

```sh
python -m flask --app backend.wsgi:app db upgrade
```

Миграция добавляет токен, счётчик `checked_in_count` и журнал
`reservation_admissions`. Данные броней сохраняются, счётчики существующих
броней начинаются с нуля. Токен старой брони создаётся при первом запросе билета.
Для новых броней он генерируется при создании, но выдача пользователю и вход
доступны только при выполнении правил ниже. `db.create_all()` не заменяет
миграцию для существующей БД. Downgrade удаляет историю входов и данные билетов.

## Получение билета пользователем

Требуется `Authorization: Bearer <JWT владельца брони>`.
Другой пользователь, в том числе администратор, получает 404.

```http
GET /api/user/reservations/42/ticket
```

Пример ответа (токен демонстрационный):

```json
{
  "ticket": {
    "reservation_id": 42,
    "session_id": 7,
    "event_id": 3,
    "event_title": "Прогулка по городу",
    "session_start_datetime": "2026-11-28T18:30:00",
    "full_name": "Анна Смирнова",
    "participants_count": 3,
    "checked_in_count": 0,
    "remaining_count": 3,
    "status": "valid",
    "can_enter": true,
    "qr_payload": "ukno:ticket:v1:<43 символа случайного токена>",
    "qr_svg_url": "/api/user/reservations/42/ticket/qr"
  }
}
```

`GET /api/user/reservations/42/ticket/qr` возвращает `image/svg+xml`.
QR кодирует `qr_payload`: версия формата и случайный токен из 32 случайных байт,
без имени, email или телефона. Повторные запросы возвращают тот же билет.
Токен не является JWT пользователя и не даёт доступа к его аккаунту.
Ответы содержат `Cache-Control: private, no-store`.

Для платного сеанса требуется `is_paid=true`; бесплатный сеанс не требует
связанного платежа. Отменённые брони, неактивные/неодобренные события не допускаются.
Если билет уже полностью использован, владелец может видеть его с `fully_used`.
Для остальных недоступных броней выдача QR возвращает 409.

## Проверка администратором

Требуется JWT администратора. Токен передаётся в **JSON**, не в URL или query,
чтобы он не попадал в access-логи и историю браузера.

```http
POST /api/admin/reservations/tickets/check
Content-Type: application/json
Authorization: Bearer <JWT администратора>

{"ticket": "ukno:ticket:v1:<токен из QR>"}
```

Допускается также чистый токен без префикса. Событие и сеанс определяются
автоматически по билету. Необязательный `session_id` сохраняется для API-клиентов,
которым нужна дополнительная проверка на конкретный сеанс; несовпадение даст `wrong_session`.
Успешная проверка возвращает `{"ticket": {...}}` с теми же данными о броне
и счётчиками, но без `qr_payload` и ссылки на QR.

| `status` | Значение |
|---|---|
| `valid` | Никто ещё не вошёл, вход разрешён |
| `partially_used` | Вошла часть группы, остальные могут войти |
| `fully_used` | Все участники уже вошли |
| `wrong_session` | Билет на другой сеанс |
| `cancelled` | Бронь отменена |
| `unpaid` | Платный сеанс не оплачен |
| `unavailable` | Сеанс/событие недоступны, событие неактивно или не одобрено |

`can_enter` истинен только для `valid` и `partially_used`.
Известный билет с запретом входа проверяется с HTTP 200 и соответствующим статусом.
Некорректный формат — 400, неизвестный токен — 404.
Проверка не расходует входы и не создаёт записи в журнале.

## Регистрация входа

```http
POST /api/admin/reservations/tickets/check-in
Content-Type: application/json
Authorization: Bearer <JWT администратора>

{
  "ticket": "ukno:ticket:v1:<токен из QR>",
  "session_id": 7,
  "count": 2,
  "request_id": "735d7c36-c0bf-4c41-95c3-1c0ed5b3dafa"
}
```

`count` — положительное целое количество входящих сейчас, не накопительный итог.
`request_id` — UUID операции в стандартной нижнерегистровой записи.
Ответ HTTP 200 содержит:

```json
{
  "ticket": {
    "reservation_id": 42,
    "session_id": 7,
    "participants_count": 3,
    "checked_in_count": 2,
    "remaining_count": 1,
    "status": "partially_used",
    "can_enter": true
  },
  "admission": {
    "admission_id": 15,
    "request_id": "735d7c36-c0bf-4c41-95c3-1c0ed5b3dafa",
    "participants_count": 2,
    "admin_user_id": 1,
    "admitted_at": "2026-11-28T13:25:00+00:00"
  },
  "replayed": false
}
```

Для краткости в примере не показаны остальные поля `ticket` из проверки.
Остаток меньше `count`, запрещённый билет или чужой сеанс дают HTTP 409.
При конфликте никого не отмечаем: весь запрос выполняется целиком или не выполняется.

Повтор с тем же `request_id`, билетом, сеансом и количеством возвращает
исходную запись `admission` и `replayed=true`, без нового списания. Поле `ticket`
показывает текущее состояние, в том числе последующие входы других гостей.
Повтор того же UUID с другим количеством/сеансом даёт 409.
При следующей самостоятельной операции, например входе третьего участника,
нужен новый UUID.

Счётчик увеличивается условным SQL UPDATE в одной транзакции с журналом.
Параллельные сканирования не могут превысить количество участников; уникальный
ключ запроса защищает от двойного учёта. Проверка билета не резервирует остаток:
между проверкой и входом он может измениться, поэтому frontend должен обрабатывать 409.

## История

```http
GET /api/admin/reservations/42/admissions
```

Только администратор: `{"ticket": {...}, "admissions": [...]}`.
Каждая запись содержит количество, администратора и время **UTC**.
Удаление брони удаляет её журнал. Если учётная запись администратора удалена,
его ID в сохранённом журнале становится `null`.

## Что потребуется на frontend

1. В карточке своей брони запросить билет и показать количество вошедших/остаток.
2. Загрузить `qr_svg_url` через авторизованный `fetch`/Axios как Blob и показать
   через `URL.createObjectURL`; простой `<img src>` не отправит JWT из заголовка.
   При закрытии карточки освободить Blob URL.
3. В админке открыть камеру и отправить прочитанный QR на `/check` без выбора сеанса.
4. Показать имя, событие и остаток. Дать выбрать `count` от 1 до `remaining_count`.
5. По подтверждению создать `crypto.randomUUID()` и вызвать `/check-in`, передав
   `session_id` из ответа `/check`.
   Блокировать кнопку на время запроса. При сетевом повторе использовать тот же
   UUID, при следующей операции — новый.
   `replayed=true` означает «этот вход уже зарегистрирован»: это не разрешение
   пропустить дополнительных людей по тому же подтверждению.
6. Показывать подтверждённый сервером остаток; при 409 повторно проверить билет.

Во встроенной Flask-админке (`/admin-panel/`) раздел «Брони» теперь содержит:

- Адаптивные фильтры и Excel-выгрузку.
- «Проверить QR-билет»: автоматическое определение сеанса, сканирование камерой, загрузку изображения
  или ручной ввод содержимого QR.
- «QR-билет» у каждой брони: просмотр кода и счётчиков, отметку входа группы.

Для просмотра администратором добавлены защищённые маршруты:
`GET /api/admin/reservations/<id>/ticket` и `GET /api/admin/reservations/<id>/ticket/qr`.
Первый возвращает билет со ссылкой на второй; оба требуют роль администратора.
Для отменённой/неоплаченной платной брони они возвращают 409.
Пользовательские маршруты по-прежнему доступны только владельцу.

Камера требует HTTPS (или localhost) и разрешения браузера. Изображения
декодируются локально библиотекой jsQR 1.4.0; на API отправляется только код.
Библиотека и лицензия лежат в `backend/static/vendor`, без runtime-зависимости от CDN.
При закрытии окна камера останавливается. При сетевой ошибке кнопка повтора
сохраняет тот же `request_id`, исключая повторный учёт.

Отдельная Vue-админка этими изменениями не обновляется.
Подтверждение брони теперь содержит QR: встроенный PNG с Content-ID и отдельное
вложение `ticket-<id>.png`, плюс существующий файл `reservation.ics`. Пользователь
может показать QR из письма или открыть PNG даже без входа в личный кабинет.
Это тот же постоянный билет; дополнительные билеты и места при отправке письма
не создаются. Платные брони получают письмо после успешной оплаты, бесплатные —
после создания. Повторный webhook оплаты не создаёт повторной отправки.
Старые письма автоматически не переотправляются.

Пока не добавлены: офлайн-проверка,
возврат ошибочно отмеченного входа и ограничения по времени относительно начала
сеанса. Время сеанса передаётся без смены часового пояса, как в существующих API.
При отметке входа проверяется сеанс из билета, а не временное окно. Копия QR предъявима как билет;
при необходимости администратор сверяет имя на месте.
